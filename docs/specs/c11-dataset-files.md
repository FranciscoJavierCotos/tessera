# C11 — Dataset files & schema history

**Status:** approved design · **Depends on:** C02 · **Milestone:** M1

## 1. Intent

**The user asked for:** uploading a `.csv` or `.parquet` file to a dataset,
stored in Supabase, with its schema read and applied to the dataset's columns
automatically. A dataset has **one current file**; uploading again keeps the
old file and records how the schema changed. Manual column edits are recorded
in the same history.

**Success:** drop `orders.parquet` on "New dataset", see its columns with types,
add descriptions and PII flags, save; later upload `orders_v2.parquet`, review
`+ added / − removed / ~ type changed`, confirm; the History tab shows both
versions with a diff and the Files tab downloads either file.

### Decisions

| Question                     | Decision                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Role of the file             | One **current** file per dataset; every upload is a new immutable version.                                                            |
| What the history tracks      | **Schema only** (columns: name, type, description, PII). Asset metadata history belongs to C07's entity history.                       |
| Upload vs existing columns   | **File is the source of truth, reviewed first**: a diff dialog; descriptions and PII flags carry over by name (case-insensitive).     |
| Limits (Supabase Free plan)  | **50 MB** per file; keep the **10 newest files** per dataset; older files are purged from Storage, their schema snapshots stay forever. |
| Where uploads happen         | On **New dataset** (prefills name, qualified name, columns) and on an existing dataset ("Upload new version").                        |
| Where parsing happens        | **In the browser** (`hyparquet` footer read, `papaparse` streamed in chunks); the file goes **directly to Storage** via a signed upload URL. |

**Why browser-side:** Next.js server actions accept 1 MB by default and Vercel
functions ~4.5 MB, so a 50 MB file cannot pass through our server. A
client-parsed schema is no less trustworthy than typing the columns by hand,
which members can already do; the database checks that the stored object
exists at the expected path.

### Out of scope

Data row preview, restoring an old schema version, gzip/`.tsv`/Excel/JSON
files, schema drift alerts, asset-metadata history (C07), server-side
re-parsing.

## 2. Data model (one migration)

### Storage bucket `dataset-files`

- Private, `file_size_limit` 50 MB, `allowed_mime_types`: `text/csv`,
  `application/vnd.apache.parquet`. The client always sends one of these
  from the detected format (browsers report CSV and Parquet
  inconsistently).
- Object path: `{workspace_id}/{asset_id}/{file_id}/{safe filename}`; the
  filename is sanitised to `[A-Za-z0-9._-]` for the key, the original name
  is kept in `dataset_files.filename` and used for downloads.
- `private.dataset_file_asset(object_name)` (security definer) parses the path
  and returns the asset id only when folders 1–3 are uuids **and** the asset
  is a dataset in the workspace named by folder 1; otherwise `null`.
- Policies on `storage.objects`:
  - select: `bucket_id = 'dataset-files' and private.can_read_entity(private.dataset_file_asset(name))`
  - insert: `bucket_id = 'dataset-files' and private.can_write_entity(private.dataset_file_asset(name))`
  - **no** update policy (versions are immutable), **no** delete policy
    (only the service role deletes: retention and asset deletion).

### `dataset_files`

| column         | type                                 | notes                                                           |
| -------------- | ------------------------------------ | --------------------------------------------------------------- |
| `id`           | uuid pk                              | generated by the server action before upload (used in the path) |
| `asset_id`     | uuid                                 | composite FK `(asset_id, workspace_id, asset_kind)` → `assets`  |
| `workspace_id` | uuid                                 |                                                                 |
| `asset_kind`   | `asset_kind` default `dataset`       | check `= 'dataset'`                                             |
| `version`      | integer                              | 1, 2, 3…; unique `(asset_id, version)`; highest = current       |
| `storage_path` | text unique                          | must equal the canonical path for `(workspace, asset, id)`      |
| `filename`     | text                                 | 1–255 chars, no `/`                                             |
| `format`       | enum `dataset_file_format` `csv\|parquet` |                                                            |
| `size_bytes`   | bigint                               | read from the stored object's metadata, `0 <= size <= 52428800` |
| `row_count`    | bigint null                          | `>= 0`                                                          |
| `uploaded_by`  | uuid → profiles, `on delete set null` | default `auth.uid()`                                            |
| `uploaded_at`  | timestamptz default `now()`          |                                                                 |
| `purged_at`    | timestamptz null                     | set when retention deletes the stored object                    |

RLS: select with `can_read_entity(asset_id)`; insert with
`can_write_entity(asset_id)` + `uploaded_by = auth.uid()`; no update or
delete for `authenticated` (`purged_at` is set by the service role). A
before-insert trigger (security definer) requires the object to exist in
`dataset-files` at `storage_path` under the row's workspace/asset/id prefix
and fills `size_bytes` from its metadata, so even a direct insert cannot
point at a missing or foreign file.

### `dataset_schema_versions`

| column         | type                              | notes                                                |
| -------------- | --------------------------------- | ---------------------------------------------------- |
| `id`           | uuid pk                           |                                                      |
| `asset_id`     | uuid                              | same composite FK as above, `on delete cascade`      |
| `workspace_id` | uuid                              |                                                      |
| `asset_kind`   | `asset_kind` default `dataset`    |                                                      |
| `version`      | integer                           | unique `(asset_id, version)`                         |
| `columns`      | jsonb                             | array of `{name, data_type, description, is_pii}`    |
| `source`       | enum `schema_change_source` `manual\|file` |                                             |
| `file_id`      | uuid null → `dataset_files`       | set when `source = 'file'`                           |
| `created_by`   | uuid → profiles, `on delete set null` | default `auth.uid()`                             |
| `created_at`   | timestamptz default `now()`       |                                                      |

RLS: select with `can_read_entity(asset_id)`; insert with
`can_write_entity(asset_id)` (only reached through `set_dataset_columns`);
**append-only**: no update or delete for `authenticated`.

### Function changes

- `set_dataset_columns(asset, columns, source default 'manual', file_id default null)`:
  replaces the two-argument version (drop + create; named-argument calls keep
  working). After writing the columns it builds the snapshot from
  `dataset_columns` ordered by `ordinal` and inserts a
  `dataset_schema_versions` row **only if** it differs from the latest
  snapshot (or none exists). Concurrent writers serialise on
  a per-asset transaction advisory lock.
- `create_asset` / `update_asset`: unchanged signatures; they call
  `set_dataset_columns` with the defaults (source `manual`).
- New `add_dataset_file(asset, file_id, storage_path, filename, format, row_count, columns)`
  (security invoker): checks the asset is an editable dataset, takes a
  per-asset transaction advisory lock, inserts `dataset_files` with the next
  version (the trigger verifies the object), calls
  `set_dataset_columns(asset, columns, 'file', file_id)`, returns the file
  row. Errors: `42501` not editable, `P0002` object missing.
- An empty snapshot is never the first one (a dataset created without
  columns has no history until it gets some).
- Backfill: every existing dataset with columns gets a v1 `manual` snapshot.
- View `catalog_assets` is unchanged.

### Retention & deletion (server, service-role client scoped by workspace)

- After `add_dataset_file` succeeds, `purgeOldDatasetFiles(workspaceId, assetId)`
  lists the dataset's files with `purged_at is null` beyond the newest 10,
  removes their objects through the Storage API and sets `purged_at`.
  Failures are logged and retried by the next upload; they never fail the
  upload.
- `deleteAsset` removes every object under `{workspace_id}/{asset_id}/`
  before deleting the entity (rows cascade).
- An upload that never gets committed leaves an orphan object; accepted for
  now (documented; a cleanup job can come with `pg_cron` later).

## 3. UI flows

### A. New dataset from a file (`/catalog/new`, kind dataset)

1. Optional drop zone "Start from a CSV or Parquet file" above the form;
   keyboard-accessible file button; `.csv`/`.parquet`, ≤ 50 MB.
2. Parse in the browser with a progress state (CSV streamed in chunks).
3. Prefill: name from the filename stem, qualified name `files.<slug>`
   (editable; duplicates give the existing error), columns into the existing
   `ColumnsEditor`; summary line `orders.parquet · 12.4 MB · 1,204,331 rows ·
   14 columns` with "Remove file".
4. Submit: create the dataset **without columns** → `prepareDatasetFileUpload`
   (signed upload URL) → upload with progress → `commitDatasetFile` with the
   edited columns → redirect to the asset. If the upload or commit fails after
   creation, redirect to the asset page with an error toast and the Files tab
   offers "Retry upload" (the dataset is kept).

### B. Upload a new version (existing dataset)

- "Upload new version" on the Files and Columns tabs, for users who can edit.
- After parsing, a review dialog shows `diff(current, file)`: added, removed
  (warning when they carry descriptions or PII), type changed, unchanged
  (collapsed). Descriptions and PII flags carry over by name and stay
  editable inline; new columns can be flagged PII.
- Confirm → prepare → upload → commit → retention → refresh.

### C. Files tab (datasets)

- Current file card: filename, format, size, rows, uploader, date, Download
  (signed URL, 60 s).
- Previous versions table: version, filename, size, uploader, date,
  Download or "File removed (retention)".
- Empty state: "No file attached — upload one to fill the schema
  automatically."

### D. History tab (datasets)

- Timeline newest first: `v4 · from file orders_v4.parquet` or
  `v3 · manual edit`, author, relative time.
- Expand: diff against the previous snapshot (added, removed, type,
  description, PII changes); "View columns" shows the full snapshot.
- Empty state for datasets with no columns yet.

## 5. Error handling

| Case                                   | Behaviour                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------- |
| Wrong extension or > 50 MB             | Rejected before parsing, inline message.                                      |
| Unreadable Parquet / CSV without header | Parser error shown in the drop zone; nothing uploaded.                        |
| Duplicate or blank column names        | Parser error naming the columns.                                              |
| More than 500 columns                  | Rejected (`MAX_COLUMNS` in `asset/schema.ts`).                                |
| Upload network failure                 | Error with "Retry"; no DB row written.                                        |
| Commit fails (object missing, RLS)     | Error toast; the object is orphaned (see retention note).                     |
| Viewer / other workspace               | Buttons hidden; DB and Storage policies deny (tested).                        |
| Retention purge fails                  | Logged; upload still succeeds; next upload retries.                           |

## 6. Testing

- **Unit (Vitest):** `parse-csv` (delimiters, inference per type, mixed
  columns fall back to `STRING`, quoted fields, errors), `parse-parquet`
  against committed fixtures (flat, nested, decimal, timestamp),
  `schema-diff` and carry-over, `limits`, Zod schemas.
- **DB (`tests/db/dataset-files.test.ts`):** snapshot written on create,
  on change, **not** on a no-op save; `add_dataset_file` versions increase
  and require the stored object; cross-workspace read/upload denied; viewer
  cannot upload; history rows cannot be updated or deleted; storage path
  from another workspace rejected.
- **E2E (`tests/e2e/dataset-files.spec.ts`):** new dataset from
  `orders.csv` → columns appear; upload `orders_v2.parquet` → review diff →
  confirm → History shows v2 with the type change → Files downloads v1.
- **Fixtures:** no committed binaries: CSV strings inline, Parquet built in
  the test with `hyparquet-writer` (`parquetWriteBuffer`).
